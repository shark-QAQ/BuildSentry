## 1. 设计目标与原则

### 1.1 设计目标

| 目标         | 说明                                           |
| :----------- | :--------------------------------------------- |
| **高准确率** | 违规点召回率 ≥ 90%，条款引用正确率 ≥ 95%       |
| **低延迟**   | 单次审核（5000字方案）响应时间 ≤ 30秒          |
| **可追溯**   | 每项违规结论必须可追溯到具体规范条文           |
| **可扩展**   | 支持新增规范、新增审核维度，无需重新训练全模型 |
| **数据安全** | 全部推理在本地/专有云完成，施工方案不泄露      |

### 1.2 设计原则

1. **模块化与解耦**：各功能模块独立开发、独立部署、独立升级
2. **微调 + RAG 双引擎**：微调模型负责“理解与推理”，RAG负责“检索与溯源”，各司其职
3. **离线优先**：V1.0以离线批量审核为主，在线API为辅
4. **可观测性**：全链路日志、性能监控、审核结果审计

## 3. 核心模块详细设计

### 3.1 文档解析模块 (Document Parser)

**职责**：将用户上传的施工方案（DOCX/PDF）转换为结构化纯文本。

**技术选型**：
- PDF解析：`pypdf` / `pymupdf`
- DOCX解析：`python-docx`
- OCR（可选）：`pytesseract`（处理扫描版PDF）

**处理流程**：
1. 文件格式识别
2. 文本提取与编码检测
3. 章节结构识别（基于标题层级）
4. 输出：带章节标记的纯文本 + 原始元数据

**输出格式**：
```json
{
  "doc_id": "SHT-20260908-001",
  "title": "深基坑专项施工方案",
  "sections": [
    {"level": 1, "title": "工程概况", "content": "..."},
    {"level": 2, "title": "地质条件", "content": "..."}
  ],
  "raw_text": "...",
  "word_count": 5200
}
```

### 3.2 规范知识库模块 (Knowledge Base)

**职责**：管理施工规范条文的结构化存储与向量检索。

**数据模型**：

```sql
-- 规范主表
CREATE TABLE specifications (
    id SERIAL PRIMARY KEY,
    spec_name VARCHAR(200) NOT NULL,      -- 规范全称
    spec_code VARCHAR(50) NOT NULL,       -- 规范编号 (如 JGJ 59-2011)
    version VARCHAR(20),
    publish_date DATE,
    UNIQUE(spec_code, version)
);

-- 条文表
CREATE TABLE clauses (
    id SERIAL PRIMARY KEY,
    spec_id INT REFERENCES specifications(id),
    article_id VARCHAR(50) NOT NULL,      -- 条文编号 (如 3.11.3)
    chapter VARCHAR(100),                  -- 所属章节
    content TEXT NOT NULL,                 -- 条文原文
    is_mandatory BOOLEAN DEFAULT FALSE,   -- 是否强制性条文
    keywords TEXT[],                       -- 关键词数组
    UNIQUE(spec_id, article_id)
);

-- 向量索引 (Chroma/PGVector)
-- 每条clause对应一个向量embedding
```

**条文级切分策略**：
- 以规范条文（条款）为最小语义单元
- 控制单条 chunk 约 300-500 tokens
- 保留 metadata：规范名称、规范缩写、条文编号、章节、是否为强制性

**检索策略**：
- 向量检索 Top-K = 5
- 相似度阈值 = 0.6（低于阈值的结果不进入生成阶段）
- 混合检索（可选）：BM25关键词检索 + 向量检索

### 3.3 微调训练模块 (Fine-tuning Module)

**职责**：基于 QLoRA 技术微调基座模型，使其具备施工安全审核的专业能力。

**技术架构**：

```
┌─────────────────────────────────────────────────────────────┐
│                    LLaMA-Factory 训练流水线                  │
├─────────────────────────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐        │
│  │ 数据准备    │→│ QLoRA训练   │→│ 模型融合    │        │
│  │ (JSONL)     │  │ (4-bit)     │  │ (Merge)     │        │
│  └─────────────┘  └─────────────┘  └─────────────┘        │
│         │               │               │                  │
│         ▼               ▼               ▼                  │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              配置管理 (YAML + CLI)                  │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

**训练配置**（基于 LLaMA-Factory）：

| 参数                  | 值                             | 说明                       |
| :-------------------- | :----------------------------- | :------------------------- |
| 基座模型              | Qwen2.5-7B-Instruct            | 中文能力强，支持128K上下文 |
| 微调方法              | QLoRA (4-bit)                  | 显存占用降低70%+           |
| LoRA秩 (r)            | 16                             | 平衡效果与参数量           |
| LoRA Alpha            | 32                             |                            |
| Target Modules        | q_proj, k_proj, v_proj, o_proj | Qwen的注意力层             |
| 学习率                | 2e-4                           |                            |
| Batch Size            | 2 (per device)                 |                            |
| Gradient Accumulation | 4                              | 有效batch=8                |
| Epochs                | 3-5                            |                            |
| Max Sequence Length   | 4096                           | 支持长段落审核             |

**数据格式**（Alpaca格式，含CoT推理链）：
```json
{
  "instruction": "你是一名资深建筑施工安全审核专家。请根据规范要求审核以下施工方案段落，找出违规点并给出整改建议。",
  "input": "【方案原文】基坑开挖深度6米，采用放坡开挖，坡率1:0.8。基坑周边3米范围内堆放钢筋模板，堆高2米。",
  "output": "【审核结论】不通过。\n\n违规项1：基坑周边堆载违规。\n- 条款：JGJ 59-2011 第3.11.3条\n- 风险等级：高\n- 整改建议：立即移除坑边堆载，材料应堆放于坑边5米外。"
}
```

### 3.4 审核推理模块 (Audit Engine)

**职责**：接收施工方案段落，结合RAG检索结果和微调模型，输出结构化审核意见。

**推理流程**：

```
输入: 施工方案段落 P
  │
  ▼
Step 1: 关键词提取
  │  提取 P 中的工程实体词 (基坑、脚手架、模板...)
  ▼
Step 2: RAG检索
  │  用 P 的向量在规范库中检索 Top-5 相关条文
  │  输出: 条文列表 C = [c1, c2, c3, c4, c5]
  ▼
Step 3: Prompt构建
  │  组装 Prompt:
  │  "你是一名审核专家。请根据以下规范条文审核施工方案：
  │   【规范条文】{c1}\n{c2}\n...
  │   【施工方案】{P}
  │   请输出JSON格式的审核结果。"
  ▼
Step 4: 模型推理
  │  调用微调模型 (vLLM/Ollama)
  │  参数: temperature=0.1 (低随机性)
  │        max_tokens=1024
  ▼
Step 5: 结果解析与校验
  │  解析 JSON 输出
  │  校验引用的条款编号是否存在于知识库
  │  若条款不存在 → 标记为"疑似风险，建议人工复核"
  ▼
输出: 结构化审核意见
```

**Prompt 模板**（核心）：
```
你是一名资深建筑施工安全审核专家。请根据以下规范条文，审核输入的施工方案段落。

【规范条文】
{retrieved_clauses}

【施工方案段落】
{paragraph}

请按以下JSON格式输出审核结果：
{
  "has_violation": true/false,
  "violations": [
    {
      "clause": "规范编号 + 条文编号",
      "clause_content": "条文原文",
      "risk_level": "高/中/低",
      "description": "违规描述",
      "suggestion": "整改建议"
    }
  ],
  "summary": "综合结论"
}

注意：
1. 只引用上述规范条文中存在的内容，严禁编造条款编号
2. 若无法确定是否违规，输出 has_violation=false 并在 summary 中说明
```

### 3.5 结果聚合与报告生成模块 (Report Generator)

**职责**：将各段落的审核结果聚合、去重、排序，生成最终审核意见书。

**处理逻辑**：
1. **去重**：相同条款的违规项合并
2. **风险排序**：高风险 > 中风险 > 低风险
3. **综合结论判定**：
   - 存在高风险项 → **不通过**
   - 仅存在中/低风险项 → **有条件通过**
   - 无违规项 → **通过**
4. **报告生成**：JSON结构化数据 → HTML/PDF（带公章样式）

**输出格式**：
```json
{
  "doc_id": "SHT-20260908-001",
  "audit_time": "2026-09-08T14:30:00Z",
  "conclusion": "不通过",
  "high_risk_count": 2,
  "medium_risk_count": 1,
  "low_risk_count": 0,
  "violations": [
    {
      "id": "V-001",
      "clause": "JGJ 59-2011 第3.11.3条",
      "clause_content": "基坑周边1.2米范围内严禁堆载...",
      "risk_level": "高",
      "location": "第3.2节 基坑支护",
      "description": "基坑周边3米范围内堆放钢筋模板，堆高2米",
      "suggestion": "立即移除坑边堆载，材料应堆放于坑边5米外"
    }
  ],
  "report_url": "/reports/SHT-20260908-001.pdf"
}
```

## 5. 关键技术决策与理由

### 5.1 为什么选择 Qwen2.5-7B？

| 考量         | 说明                                       |
| :----------- | :----------------------------------------- |
| **中文能力** | Qwen系列在中文理解和生成上处于开源模型前列 |
| **长上下文** | 支持128K上下文，可一次性处理完整章节       |
| **商用友好** | 采用Apache 2.0许可证，可自由商用           |
| **生态完善** | 与LLaMA-Factory、vLLM等工具深度集成        |

### 5.2 为什么选择 QLoRA 而非全量微调？

| 考量         | 说明                                       |
| :----------- | :----------------------------------------- |
| **显存约束** | QLoRA仅需16-24GB显存即可微调7B模型         |
| **训练效率** | 相比全量微调，训练速度提升3.7倍            |
| **模型切换** | 不同规范体系可训练不同LoRA适配器，快速切换 |

### 5.3 为什么采用「微调 + RAG」双引擎？

| 考量           | 说明                                         |
| :------------- | :------------------------------------------- |
| **微调的优势** | 让模型深度理解审核任务的格式、风格和推理逻辑 |
| **RAG的优势**  | 保证条款引用的准确性，杜绝编造条款           |
| **协同效应**   | 微调模型负责"怎么审"，RAG负责"用什么审"      |

### 5.4 为什么选择 LLaMA-Factory？

| 考量       | 说明                                       |
| :--------- | :----------------------------------------- |
| **低代码** | 提供Web UI和CLI，降低使用门槛              |
| **全流程** | 覆盖数据准备、训练、融合、推理、部署全链路 |
| **模块化** | 架构设计注重模块化和扩展性                 |


## 6. 数据流与状态管理

### 6.1 审核任务状态机

```
  [待处理] ──→ [解析中] ──→ [审核中] ──→ [已完成]
      │            │            │            │
      │            │            │            ├──→ [成功] → 返回结果
      │            │            │            └──→ [失败] → 返回错误
      │            │            │
      │            │            └──→ [超时] → 返回超时提示
      │            │
      │            └──→ [解析失败] → 返回格式错误提示
      │
      └──→ [取消] (用户主动取消)
```

### 6.2 数据存储设计

| 数据类型       | 存储方案            | 说明                  |
| :------------- | :------------------ | :-------------------- |
| 规范条文       | PostgreSQL + Chroma | 结构化存储 + 向量索引 |
| 训练数据集     | 文件系统 (JSONL)    | 版本化管理            |
| LoRA适配器     | 文件系统/对象存储   | 按规范版本命名        |
| 审核记录       | PostgreSQL          | 含完整审核报告JSON    |
| 上传的方案文件 | 文件系统/对象存储   | 保留原始文件          |
| 系统日志       | ELK / Loki          | 全链路可观测          |
