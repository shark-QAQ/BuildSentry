## 1. 项目背景与目标

### 1.1 背景痛点
- **规范庞杂**：施工现场涉及《JGJ 59》、《GB 50202》等数百部国标/行标，人工记忆全量条文几乎不可能。
- **审核低效**：监理/安全员审核一份《深基坑专项方案》平均耗时 4-6 小时，且极易遗漏隐藏在附录中的强制性条款。
- **经验断层**：资深审核专家的经验难以快速复制给一线年轻安全员。

### 1.2 项目愿景
打造工程建设领域的**“智能合规哨兵”**。通过微调大语言模型，使系统能够像资深安全专家一样，自动阅读施工方案，精准识别违规风险，并给出法定整改依据，将单份方案审核时间压缩至 **5分钟以内**。

### 1.3 核心定位（边界定义）
- **我们是“审核员”**：拒绝闲聊，拒绝创作施工方案。
- **核心动作**：**“找茬”**。输入一份方案，输出一份结构化的《违规整改通知单》。
- **原则**：**零容忍幻觉**。引用的条款编号必须百分百真实存在。

## 3. 功能需求详情（核心）

### 3.1 文档智能解析（预处理）
- **功能**：支持上传 `.docx`、`.pdf` 格式的施工方案。
- **要求**：自动提取纯文本内容，保留章节结构（如“4.2.1 放坡系数”），剔除页眉页脚等无关噪音。
- **交互**：上传后展示文本预览窗口，允许用户手动修正OCR/解析错误。

### 3.2 合规性深度审核（AI 核心引擎）—— **重中之重**
- **功能**：系统根据内置规范库，对方案文本进行逐段/全局逻辑审查。
- **审核维度**（至少包含）：
  1.  **定量指标违规**：如放坡系数小于规范值、脚手架立杆间距超标。
  2.  **定性措施缺失**：如深基坑未提及“降排水措施”、高支模未提及“沉降观测点”。
  3.  **逻辑自洽性**：方案中提到的“施工工期”与“混凝土养护周期”是否矛盾。
- **输出格式**：必须输出 JSON 结构化数据，而非大段散文，便于前端渲染。

### 3.3 生成《审核意见书》（输出层）
- **功能**：一键生成带红章的电子版审核报告。
- **报告内容**：
  - **综合结论**：通过 / 有条件通过 / 不通过。
  - **违规清单（列表）**：展示【风险等级】、【违规条款编号】、【违规原文定位】、【违规描述】、【强制整改建议】。
  - **条款溯源**：每个违规项必须附带规范原文截图/引用链接（RAG溯源）。

### 3.4 知识库与条款检索（RAG增强）
- **功能**：管理员可上传最新的 PDF 规范，系统自动切片向量化。
- **要求**：在微调模型推理时，优先从向量库检索 Top-5 最相关条文，作为“上下文背景”喂给模型，减少大模型固有的“编造条款”问题。

## 4. 非功能需求（技术硬指标）

| 指标项             | 规格要求                        | 备注                           |
| :----------------- | :------------------------------ | :----------------------------- |
| **审核准确率**     | 违规点召回率（Recall）≥ **90%** | 漏报比误报更严重               |
| **条款引用准确率** | 引用条款编号正确率 ≥ **95%**    | 严禁胡编乱造标准号             |
| **单次响应速度**   | ≤ **30秒**                      | 方案字数按 5000字计            |
| **上下文长度**     | 支持 **8K~32K** tokens          | 能够一次性阅读完整的“章节”     |
| **并发支持**       | V1.0 支持 **5路** 并发审核      | 满足小型项目组使用             |
| **数据隐私**       | 全部推理在**本地/专有云**完成   | 施工图纸/方案涉密，严禁外传API |

## 5. 数据构建策略（AI工程的命脉）

这是V1.0能否成功的关键。我们不走“通用问答”，走“专家推理”。

### 5.1 数据来源
1.  **公开法规库**：住建部公开的强制性条文。
2.  **历史审核记录（高价值）**：脱敏后的历史监理整改单（如果项目中有）。
3.  **专家标注（冷启动）**：聘请安全专家编写 200 条典型违规案例。

### 5.2 数据格式（指令微调格式）
数据必须包含模型的“推理思维链（CoT）”，格式如下：

```json
{
  "instruction": "你是一名资深安全审核专家。请根据《JGJ 59-2011》标准，审核输入的施工方案片段。找出违规点，并按JSON格式输出{违规条款, 风险等级, 整改建议}。",
  "input": "（此处放入待审核的方案段落）",
  "output": "（此处放入包含推理过程和结论的JSON字符串）"
}
```

### 5.3 数据规模
- **冷启动阶段**：构建 **500条** 高质量“违规案例”。
- **V1.0 上线目标**：扩充至 **2000条** 覆盖房建、市政路桥的通用违规场景。

## 6. 技术选型与架构（初定）

| 层级           | 技术组件                    | 选择理由                                    |
| :------------- | :-------------------------- | :------------------------------------------ |
| **基座模型**   | **Qwen2.5-7B/14B-Instruct** | 中文理解能力强，支持超长上下文，商业友好。  |
| **微调框架**   | **LLaMA-Factory**           | 支持QLoRA，界面友好，便于我们快速迭代数据。 |
| **微调策略**   | **QLoRA (4-bit)**           | 仅需 16GB-24GB 显存即可跑动 7B 模型。       |
| **向量数据库** | **Chroma / Milvus Lite**    | 轻量级，用于挂载外部规范库进行RAG检索增强。 |
| **推理部署**   | **Ollama + vLLM**           | 支持高吞吐量推理，API 兼容 OpenAI 格式。    |
| **前端界面**   | **Gradio / Streamlit**      | 快速搭建演示Demo，方便专家验收数据。        |

## 7. 约束条件与风险预案

| 风险项                   | 应对策略                                                     |
| :----------------------- | :----------------------------------------------------------- |
| **模型幻觉（编造条款）** | 1. 强制在Prompt中限定“若找不到依据，则输出‘疑似存在风险，建议人工复核’”。<br>2. 增加RAG检索校验，将模型输出的条款与向量库进行二次比对。 |
| **数据标注质量差**       | 初期由安全工程专业的实习生或专家双盲标注，Kappa系数低于0.8则返工。 |
| **超长文档显存溢出**     | 采用“滑动窗口”或“层级摘要”策略，先让模型概括章节，再针对关键章节细审。 |

---

## 8. 交付物与验收标准（Definition of Done）

- **数据交付**：提供整理好的 500+ 条 JSONL 训练集、验证集。
- **模型交付**：提供合并后的 LoRA 适配器权重文件（或完整模型文件）。
- **代码交付**：提供基于 LLaMA-Factory 的微调脚本、评估脚本、推理 Demo 源码。
- **验收测试**：准备 20 份未参与训练的施工方案进行盲测。**要求：AI 审核出的违规点数量 ≥ 人工审核出的违规点数量的 85%。**
