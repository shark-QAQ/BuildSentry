## 二、数据管线

```
依据库          52 部法规（1983 条） + 54 部标准（5324 条）= 7307 条条文
   ↓
规则表          1212 条（量化 483 / 禁止性 729）
                + 48 条触发规则 + 368 条常见误区 + 22 条隔离名单
   ↓
① 合规基线      每个字段在该字段**全部**规则约束出的区间内随机取值
   ↓
② 受控注入      定向破坏：violation 6 : distractor 2 : negative 2
                注入记录 = ground truth（真实底稿涉密拿不到，故把因果反过来）
   ↓
③ 渲染成文档    build_materials.py：**模板确定性渲染，数字直接取自规则表**
   ↓
④ LLM 改写      本地模型把模板腔润色成公文腔（**只改措辞，数字零容忍**）
   ↓
⑤ 五道质检闸    → 训练 12000 / 评测 1500，跨任务 MD5 交集 = 0
```

**四个任务：**

| 任务 | 内容 | 训练 | 评测 |
|---|---|---|---|
| A | 单项合规判定（三态：合规/不合规/依据不足） | 5000 | 600 |
| B | 全量违规检出（整份资料包 → 违规清单 JSON） | 3000 | 500 |
| C | 法条问答 | 2000 | 200 |
| D | 多轮追问 | 2000 | 200 |

### ③ 为什么是「渲染」而不是「让 LLM 生成文档」

文档草稿由模板**确定性渲染**，所有数字直接取自规则表，LLM 只负责润色措辞。
LLM 的任务从"生成"降级为"改写"——**它不需要知道正确数字是什么**，
即便出错也只错在措辞、不会错在数值。反过来说，若让 LLM 直接生成资料文档，
它就得记住规则表里 1212 条规则的数字——这正是要避免的。

### ④ 合成路线的两条硬约束（用户明确要求）

1. **不调外部 API**，一律用本机已下载模型 + vLLM 起本地端口。
2. **合成模型不得是被测基座**（Qwen3-32B）——用被测模型生成自己的训练数据
   等同数据泄漏。本项目用 Qwen3-30B-A3B。

## 三、训练配置

```python
# 量化（BitsAndBytesConfig）
load_in_4bit=True
bnb_4bit_quant_type="nf4"
bnb_4bit_use_double_quant=True
bnb_4bit_compute_dtype=torch.bfloat16     # A6000 是 Ampere，支持 BF16

# LoRA
r=16, lora_alpha=32, lora_dropout=0.05
target_modules=[q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj]

# TrainingArguments
epochs=3, batch_size=1/卡, gradient_accumulation_steps=8
learning_rate=2e-4, max_seq_len=8192
eval_strategy="steps", eval_steps=200      # 5% 留出评测
```

**硬件与耗时**：4 × RTX A6000 48GB（卡 2,3,4,5）
——约 **29 秒/步 × 1071 步 ≈ 8.5~11 小时**。

**`max_seq_len=8192` 是必须的**：任务 B 的违规清单约 3500 字，
默认的 1024 装不下，会被静默截断。

### 为什么要用 `CUDA_VISIBLE_DEVICES` 显式指定

第一次冒烟时漏了这个，`torchrun` 默认抓了 0-3，**占用了不该用的 0、1 卡**。
多卡训练脚本必须显式指定，脚本内已注释说明。

| ② | 判定精确率 | 98.7% | **98.9%** | ≥80% |

**「可答」是什么意思**：评测集 task_b 有 **39.7%** 的参考答案在给定资料里

又高估它（掺了 1202 个纯靠模板发射、不需读资料的"命中"）。

### 5.3.1 v2 vs v3 —— 同一份清洗后参考答案上的公平对照

| | tp | fp | fn | 召回 | 精确 | 高风险漏判 | **接地闸需剔除** |
|---|---|---|---|---|---|---|---|
| v2 | 2971 | 32 | 1 | 100.0% | 98.9% | 0.00% | **1251 条** |
| **v3** | 2972 | **6** | **0** | 100.0% | **99.8%** | 0.00% | **0 条** |

**这两行要连起来读**：

- 单看指标，两代差距不大（召回都 100%，精确 98.9% → 99.8%）。
- 但 v2 是**靠护栏兜住的**——它自己每次要吐出 1251 条编造内容，
  全靠接地闸删掉才能得到上面这行数字。**v3 不需要任何修正**。
- 差别在于：护栏是**安全网**，不是**拐杖**。v2 依赖它才能用，v3 不依赖。

### 5.3.2 编造行为体检探针（task_b 前 30 条）

| 探针 | v2 | v3 |
|---|---|---|
| JSON 可解析 | 30/30 | **30/30** |
| 报出不可见字段的样本 | **30/30 = 100%** | **0/30 = 0%** ✅ |
| 条款组合多样性 | 500 条样本只有 **5 种**组合 | 30 条有 **14 种**，最大同签名簇仅 1 条 ✅ |
| 报零违规的样本数 | 0/30 | 16/30 |
| 参考答案为空的样本数 | — | **16/30** ✅ 完全吻合 |

**没有过度保守**：清洗后 39.7% 的样本参考答案为空（原为 20%，翻了一倍），
曾担心模型变得不敢报。实测前 30 条模型报 16 空 / 14 非空，
参考答案正好也是 16 空 / 14 非空——**完全吻合**。

这印证了事故报告里的判断：v2 表现出的"编造"，本质是**它忠实地学会了
我们给它的错误数据**。数据对了，行为就对了。

### 5.4 压测（TP=2，bf16 基座 + LoRA）

混合负载 60 条（短问 40 / 长资料 20），0 错误，`max_tokens=3072`、`temperature=0`。
原始数据 `data/eval/stress_report.json`。

| 并发 | 请求/秒 | 输出 tok/秒 | P50 | P95 | P99 | 均值 |
|---|---|---|---|---|---|---|
| 1 | 0.05 | 16.3 | 6.3s | 118s | 167s | 19.9s |
| 4 | 0.17 | 53.9 | 6.2s | 114s | 161s | 19.3s |
| 12 | 0.33 | 107.3 | 6.4s | 117s | 164s | 19.9s |
| 24 | 0.35 | 112.7 | 7.0s | 119s | 167s | 20.5s |

- **拐点在并发 12**：12→24 吞吐只涨 5%，再往上只堆延迟不涨吞吐。生产建议跑 12
- P50 稳定 6.2~7.0s 且几乎不随并发劣化
- P95 约 118s，是部分请求写满 `max_tokens=3072` 所致，**不是排队**
  （`Waiting: 0 reqs` 全程成立）。生产把 max_tokens 收到 1500 可显著压尾延迟

#### ⚠️ 一个会被误读的数字：v3 的「输出 tok/秒」比 v2 低

| 并发 | v2 tok/秒 | v3 tok/秒 |
|---|---|---|
| 24 | 134.7 | **112.7**（−16%） |

**这不是变慢了**，而是 v3 少吐了垃圾：

| | 平均输出长度 | 平均报出违规数 |
|---|---|---|
| v2 | 2224 字 | 8.97 条 |
| v3 | **1657 字** | **6.49 条** |

差的 **2.48 条正好等于 v2 平均每条编造的数量**（实测 2.49）。
v3 输出短了 26%，单位时间内能产出的 token 自然少了。
**真实指标全部变好**：请求/秒 0.32 → **0.35**、
P50 8.6s → **7.0s**、P95 142s → **119s**、整轮墙钟 188s → **171s**。

> 教训：**吞吐类指标必须与输出长度一起看**。单看 tok/秒 会把"少输出无用内容"
> 误判成"性能退化"。

### 5.5 必须声明的能力边界

- **以上是合成评测集上的结果，不是真实审计验收**（plan §11 明确要求声明）。
  受控注入保证了 ground truth 准确，但合成分布与真实底稿存在差距。
- 审计检查点主体是**程序性**合规（招投标/合同/施工程序），
  这是审计实务的真实分布；施工技术指标判定不在范围内（依据库无免费通道）。
- **幻觉无法绝对归零**：模型尽力 + 护栏兜底，这是设计前提而非缺陷。

## 六、踩过的坑（完整清单）

### 6.1 数据与评测（后果最重）

| 坑 | 现象 | 根因 | 修法 |
|---|---|---|---|
| **参考答案不接地** | 40% 的 task_b 参考答案在资料里不可见；模型学会对每份资料**恒定编造** 2~3 条违规，两份不同资料吐出**逐字相同**的输出 | 规则字段归属错误 + 渲染器不渲染该字段 | 18 条规则入隔离名单；护栏加**接地闸**；见 `03_*.md` |
| **闸只报告不拦截** | `gate_fail: 4000/4000` 写进了报告和数据，管线照跑 | `main()` 无返回值，退出码恒为 0 | `sys.exit(main())` |
| **隔离名单静默失效** | 合规基线自检从"零违规"变成报 5 条违规 | 名单键先用 `rule_id`，规则表一扩充 ID 全重排；后改 `法规名\|条号` 又太粗（同条款常兼有好坏规则） | 稳定键 `法规名\|条号\|方向\|值\|单位` + `load_quarantine(rules)` 主动校验，对不上即报错 |
| **隔离对注入没生效** | 隔离了但注入器照旧注入 | `injectable()` 用 `r["id"] not in quar`，quar 是字符串集合，**int 与 str 比较恒为真** | 改用 `RC.qkey(r)` |
| **不可能取值** | 15.5% 训练 / 18.7% 评测样本出现「14 名成员，专家 21 名」 | 约束只加在随机基线路径，注入路径仍是裸浮点 | 约束下沉到**唯一写入口** `set_field()` |
| **样本撞车** | 400 条 negative 样本内容完全相同 | 全部从固定 `BASELINE` 出发 | 每条样本现取随机合规基线 |
| **注入互相覆盖** | 注入记录与实际资料对不上 | 同一字段上多条规则逐条注入，后者冲掉前者 | 按**字段**去重后注入 |
| **破坏值恒定** | 1200 条只有 241 条唯一 | 同一规则的破坏值永远相同 | 加抖动，下限 10% 保证越界 |
| **预测与参考错位** | 按行对齐率仅 11.3%，三态准确率虚低到 40.7% | 并发 16 下 `as_completed` 完成顺序 ≠ 输入顺序 | 改用 `ex.map`（保持输入顺序） |
| **护栏抽不到比例字段** | 高风险覆盖率 93.6% → 77.5% | 改写后语序会变（关键词在前/数值在前两种都有），只写单向匹配 | **双向匹配** |

### 6.2 部署（详见 `02_部署形态实测结论.md`）

| 坑 | 现象 | 根因 |
|---|---|---|
| **AWQ 量化毁掉微调** | JSON 格式遵循 0/30，退化成基座 | 本项目 LoRA 改动量 ‖Δ‖/‖W‖ 仅 **0.86%**，被 int4 噪声（≈12%·σ）淹没。对照组 project01 是 2.66%，量化后正常 |
| **bf16 合并也毁掉微调** | 格式遵循 99.8% → **85.4%**，报出违规数只剩参考的 63% | Δ 被塞进 W 的 bf16 格子里，格子粒度 1.4e-4 而 Δ 的 RMS 才 2.8e-4，相对噪声 ~14%。运行时挂 LoRA 时 A/B 按各自尺度存，噪声仅 ~0.8%，**精度高 17 倍** |
| **tokenizer 格式不兼容** | 服务起不来，报 `AttributeError: 'list' object has no attribute 'keys'` | 新版 transformers 把 `extra_special_tokens` 从 dict 改成 **list** 并把 chat_template 拆到 `.jinja`，旧版 vLLM 读不了。修法见 `fix_tokenizer.py` |
| **`vllm serve` 的 model 是位置参数** | 直接报错退出 | 写成 `--model` 了 |

### 6.3 环境（详见记忆 `env-traps-pgrep-and-paths`）

| 坑 | 现象 | 修法 |
|---|---|---|
| **存在缺 `usr/` 的同名项目目录** | 若干次文件写入落到 `/data02/wangqihao/...` 空壳里，真目录留着**有 bug 的旧脚本**，排查很久 | 脚本一律**硬编码绝对路径**，不用 `Path(__file__)` 推导；写文件后立刻读回校验 |
| **`pgrep -f` 会杀掉自己的 shell** | 命令行里含该字符串，`pgrep -f` 匹配到自己，`kill -9` 把自己杀了，后续语句全部不执行 | 按 `/proc/*/exe` 真实路径判断，并排除 `bash` 与自身 PID |
| **grep 与 python 读同一文件结果不一致** | 曾据此误判代码状态 | 以 python 读回为准 |

### 6.4 抽取逻辑

| 坑 | 现象 | 修法 |
|---|---|---|
| **条号错位** | 条文编号整体偏一 | flush 时用 `cur_no` 而非 `m.group(1)` |
| **全角数字** | 4 部标准抽出 0 条 | 加 `fullwidth_fix()` |
| **目录污染** | 目录页被当成正文 | 三行目录探测 + `drop_toc()` |
| **5 级编号** | 深层条文漏抽 | CLAUSE 正则放宽到 5 段点分组 |
| **禁止性规则虚增** | 836 → 2042 条 | `不应?` 使"应"可选，导致任何"不"都命中；改回 `不应` |
| **负数阈值语义反转** | `-25℃` 变成 `25.0℃` | `fullmatch` 拒绝负号；加 `[-−－]?` |
| **技术标准用语漏抽** | 技术标准规则提取不到 | 补 不应/应不/不宜 动词与工程单位（mm/kV/Ω/Hz/℃） |

## 八、三条可迁移的教训

1. **只报告不拦截的闸等于没有闸**，而且比没有更糟——它让人以为"跑过闸了"。
   闸的正确形态是**非零退出码**。
2. **闸要验证「下游真正消费的东西」**。本项目那道闸比对的是两个都读结构化
   `material` 的函数，而真正被训练消费的是**渲染出的文档**——两边都看不到的问题，
   两侧对照永远发现不了。
3. **「参考答案合理」≠「参考答案可答」**。生成式数据的 ground truth
   必须校验「答案能否从输入推出」，而不只是「答案与注入记录是否一致」。
   模型会忠实地学到数据里的规律——**包括那些假的规律**。
