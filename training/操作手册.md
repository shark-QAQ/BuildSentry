# 服务器微调操作手册

从零到「微调后的模型跑在服务里」的完整步骤。命令都在**服务器上**执行。

阶段 0/1 不需要 GPU，可以立刻做；阶段 2 起需要 GPU。

---

## 阶段 0：前置检查

### 0.1 Python 版本（最容易踩的坑）

**训练环境不能用 3.14。** 服务侧是 3.14，但 LLaMA-Factory、torch、bitsandbytes、
flash-attn 目前都跟不上，请用 **Python 3.11 或 3.12** 建训练环境。

```bash
# 确认服务器上有 3.11/3.12
python3.12 --version || python3.11 --version
```

> 训练脚本要 import `app/` 的模块，所以脚本本身也必须能在 3.12 下解析。
> 仓库里有一条测试专门守着这件事（`TestTrainingPythonCompatibility`），
> 它会拦住意外引入的 3.14 专属语法。

### 0.2 确认模型权重可获取

```bash
# 本地已有权重（内网/离线环境走这条）
ls /path/to/models/Qwen3-8B /path/to/models/Qwen3-32B

# 没有本地权重则从 HuggingFace 拉，需要能联网
# 32B 约 65GB，8B 约 16GB，先确认磁盘和网络
df -h /path/to/models
```

若用本地路径，后面所有 `Qwen/Qwen3-8B` 都替换成该绝对路径。

### 0.3 记录显卡现状

```bash
nvidia-smi --query-gpu=index,memory.used,memory.total,utilization.gpu --format=csv
```

确认 `.env` 里的 `MODEL_GPU_EXCLUDE=0,1` 仍然符合当前实际（0、1 号卡要留给别人）。

## 阶段 1：安装训练环境

训练依赖与服务镜像隔离，装到独立虚拟环境。

```bash
cd /path/to/BuildSentry/training

python3.12 -m venv .venv-train
source .venv-train/bin/activate

pip install -U pip
pip install -r requirements.txt
```

**`flash-attn` 大概率编译失败**（要匹配 CUDA 版本、编译耗时长）。装不上就跳过：

```bash
pip install -r requirements.txt --no-deps -e . 2>/dev/null || true
grep -v flash-attn requirements.txt | pip install -r /dev/stdin
```

并记得把 `configs/qlora_sft.yaml` 里的 `flash_attn: fa2` 那一行删掉。

**验证：**

```bash
python -c "import torch, llamafactory; print('torch', torch.__version__, '| cuda', torch.cuda.is_available())"
```

`cuda` 必须是 `True`。

## 阶段 2：跑基线（决定微调是否值得做）

**不要跳过这一步。** 没有基线，训完你无法判断是变好了还是变差了。

用**学生模型**（8B）跑一批真实方案，看它现在的表现：

```bash
cd /path/to/BuildSentry
source training/.venv-train/bin/activate

python training/generate_dataset.py \
    --documents /path/to/real_plans/ \
    --output /tmp/baseline.jsonl \
    --model Qwen/Qwen3-8B \
    --limit-per-doc 10 \
    --no-thinking
```

跑完会打印统计，**重点看「解析失败」那一行**：

```
  标注段落: 42
  含违规:   8 (19.0%)
  无违规:   34 (81.0%)
  解析失败: 12 段（已丢弃，未写入）   ← 这个数字是关键
```

判读：

| 解析失败率 | 结论 |
|---|---|
| < 5% | 格式已经很稳，微调的收益主要在**判断质量**，需要专家标注才能评估 |
| 5–30% | 格式是明确短板，**微调收益最直接**，优先做 |
| > 30% | 先别训，检查 prompt 与 chat template 是否正确 |

同时也把 `/tmp/baseline.jsonl` 留着 —— 它能告诉你基座模型在无微调时能识别出多少违规，
作为后续对比的参照。

> 这一步会加载 8B（约 16GB 显存）。若与线上服务同机，先确认卡够用。

## 阶段 3：造数据（32B 教师）

用 32B 为真实方案生成候选标注。

```bash
python training/generate_dataset.py \
    --documents /path/to/real_plans/ \
    --output training/data/labeled.jsonl \
    --model Qwen/Qwen3-32B \
    --gpu auto
```

要点：

- **教师默认开启思考模式**（不加 `--no-thinking`）。思考能提升标注质量，其内容会被
  解析器自动剥离，不会写进训练目标。
- 32B 4-bit 也要约 17GB，`--gpu auto` 会按 `.env` 的排除与阈值规则挑卡。
- 数据量参考：**500–2000 个段落**是比较务实的起步规模。按每个方案 40 段算，
  大约需要 15–50 份真实施工方案。

```bash
# 想先小规模试跑
--limit-per-doc 5
```

**产出**：`training/data/labeled.jsonl`，每行一条 `{paragraph, clauses, violations}`。

## 阶段 4：人工抽检（不要跳过）

教师输出**未经复核**，直接拿来训练会把 32B 的错误固化进 8B。
合规审核场景下，这等于把「模型幻觉」写进了生产系统。

至少要做的：

```bash
# 抽查 30 条，重点看这些
head -30 training/data/labeled.jsonl | python -m json.tool --json-lines 2>/dev/null || head -3 training/data/labeled.jsonl
```

**逐条核对这几点：**

1. **条款引用是否真实存在** —— `clause_code` 和 `clause_content` 是否与 RAG 给出的条文一致。
   模型编造条款是这个任务最危险、也最常见的失败模式。
2. **是否漏报** —— 段落里明显的违规，教师有没有识别出来。
3. **风险等级是否合理** —— 不要把「建议性条款」判成 `high`。
4. **描述是否指向具体位置** —— 泛泛而谈的「建议核查」价值很低。

发现系统性问题（比如经常编造条款）就**先改 prompt 再重新生成**，不要硬着头皮往下走。

> 长期来看，服务里的**人工复核功能**（`human_review_status` + `review_comment`）
> 才是可持续的数据来源。等系统上线，真实复核记录会持续产出高质量样本。

## 阶段 5：转换与校验数据集

```bash
cd /path/to/BuildSentry
python training/prepare_dataset.py convert \
    --input training/data/labeled.jsonl \
    --output training/data/train.jsonl
```

转换会顺带做质量检查，**有问题会中止且不写文件**：

```
样本总数: 520
  含违规: 132 (25.4%)
  无违规: 388 (74.6%)
  风险等级分布: {'high': 41, 'medium': 63, 'low': 28}

校验通过

警告: 缺少这些风险等级的样本: ['low']    ← 有警告不阻断，但要留意
```

它会拦住：`risk_level` 非法值、`has_violation` 与 `violations` 矛盾、
prompt 不是本项目模板生成的、训练目标过不了推理侧解析器。

**注意分布警告**：全是违规样本会让模型倾向于无条件报违规；缺少某个风险等级，
模型在那个等级上就学不到东西。

## 阶段 6：训练

```bash
cd /path/to/BuildSentry/training
source .venv-train/bin/activate

llamafactory-cli train configs/qlora_sft.yaml
```

显存不够时的调整顺序（只改一条，别一次全改）：

1. 降 `cutoff_len`（4096 → 2048）
2. 降 `per_device_train_batch_size`，同时按比例升 `gradient_accumulation_steps`
   保持有效 batch 不变

时间参考：**1000 条样本、cutoff 2048、3 epoch，大约 1–3 小时**（A6000 单卡）。

观察 `saves/qwen3-8b-qlora/` 下的日志，`loss` 应稳步下降；
**验证损失开始回升就是过拟合**，降低 `num_train_epochs` 或 `lora_rank`。

## 阶段 8：接回服务并验证

### 8.1 指向适配器

```bash
# .env
LORA_PATH=/abs/path/to/BuildSentry/training/exports/buildsentry-8b-lora
```

### 8.2 重启并预热

```bash
# 重启服务
python start.py

# 关键：预热。model_loader 是懒加载，首次审核请求才加载模型，
# 那个请求要等十几秒到几分钟，而前端轮询 30 秒就超时。
curl -X POST "http://localhost:8000/api/v1/audit/tasks?doc_id=1" -H "Authorization: Bearer <token>"
```

### 8.3 验证微调生效

跑一批**训练时没见过**的真实方案，对比阶段 2 的基线：

```bash
python training/generate_dataset.py \
    --documents /path/to/holdout_plans/ \
    --output /tmp/after.jsonl \
    --model /abs/path/to/BuildSentry/training/exports/buildsentry-8b-lora \
    --no-thinking
```

对比两个数字：

| 指标 | 基线 | 微调后 |
|---|---|---|
| 解析失败段数 | | 应显著下降 |
| 识别出的违规数 | | 应收敛到与人工判断接近 |

**注意**：`generate_dataset.py` 用 `--model` 加载的是完整模型路径；
要测适配器，先把适配器 merge 成完整权重，或直接在服务里验证（推荐后者）。

### 8.4 检查结果标注

审核结果里的 `model_version` 字段应该是 `real-v1.0`：

- `real-v1.0` —— 全部段落由模型给出 ✓
- `simulation-v1.0` —— 走了模拟模式（模型没加载成功，检查日志）
- `mixed` —— 有段落解析失败，`conclusion_detail` 里会写明有几段

## 常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| `except expressions without parentheses...` | 训练环境是 3.12，脚本里有 3.14 语法 | 用 3.12 支持的写法，跑 `pytest tests/test_training_dataset.py` 定位 |
| 训练脚本 `import app` 失败 | 没在仓库根目录执行 | 脚本会自行把仓库根加进 `sys.path`，确认没改过 `REPO_ROOT` |
| `no kernel image is available` | 显卡架构与 torch 编译版本不匹配 | 重装匹配 CUDA 版本的 torch |
| 训练 OOM | 显存被别的服务占了 | 降 batch/cutoff，或换一张更空的卡 |
| 导出后效果没变化 | 训练/推理 prompt 不一致 | 见 README 的「切换基座模型时必须同步的位置」 |
| 服务里 `model_version` 是 `simulation-v1.0` | 模型没加载成功 | 看启动日志里的 `模型加载失败` |
| 首次审核请求超时 | 懒加载导致首次要下 16GB | 部署后先手动预热一次 |
